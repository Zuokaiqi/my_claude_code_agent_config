# Sub-agent派工规则

2026-07-25从331行砍到本版。原文在`~/.claude/_archive-rules/sub_agent_dispatch-20260725-full.md`，里面那套按体量阈值自动派工的判断树已废弃。

废弃理由：那套规则的设计对象是「不如顶级模型聪明的跨工具执行者」，而实际执行者就是主会话本身，上下文完整，派不派是现场判断，写成阈值表没有减少判断，只是多了一张每次都要对照的表。本文件只保留几条用事故换来的硬约束。

## 派不派：现场判断，需要时提议

主会话攥主线，判断和上下文都在这里。派工的唯一理由是**重**（会产生大量之后不回看的输出）或**独立**（能跟别的活并行）。够不够重按当下情况判断，不设数字阈值。

判断完主动向用户提议一句，用户点头再派。不要求用户记得有哪些agent。

可用的agent：`code-writer`（写实现）、`code-reviewer`（工程视角审查）、`ux-reviewer`（用户视角审查）、`ui-designer`（只出方案不写代码）、`general-purpose`（搜索、调研、一口气跑完的独立工作包）。

## 硬约束（违反过，有代价）

**一、调reviewer必须给行号。** 对每个修改文件写明「要看的行号区间加该位置应该是什么样」。新建文件不用给，reviewer会整文件读。

代价：历史上一次审查17个文件没给行号，reviewer陷入死循环，重复Read同一文件前30行115次。

**二、reviewer与writer的往返上限2轮。** 同一类reviewer最多调2次。第2轮仍不通过就停止自动转包，把两轮报告、writer两次改动的对比、卡住的检查项汇总给用户裁决。

代价：两边对某条检查项解读不同会无限拉锯，token烧完也不收敛。

**三、派工prompt必须带「已探明的现场」。** 主会话已经确认的位置信息（`path:line`加一句结论）写进prompt，标明直接采信、禁止重新全局探索。

代价：不带等于让agent把刚翻过的文件重新读一遍，慢且丢上下文。

**四、强交互的活不派。** subagent中途没有跟用户对话的通道。需要用户逐步确认才能往下走的活（共创式需求拆解、边看边调的界面优化、逐题讨论的答疑）留在主线，无论体量多大。

**五、明文密钥不进prompt。** 只给字段名、改动行号、占位符，让agent自己Read取值。理由和实证见`error_log.md`第1条。

## 派工模板

```
你是 <agent名>，<任务简述>。

## 输入文件（自己 Read，不要重新探索）
- <绝对路径>

## 已探明的现场（直接采信，禁止重新全局探索）
- <path:line>：<已确认的结论>

## 改动范围
- <改哪些文件、新增什么>

## 边界
- <不要动什么、不要扩散到哪>
```

调reviewer时额外给：新建文件列表（整文件读）、修改文件加行号区间加该位置应该是什么样、审查重点不超过4条。单批文件数超过6个就拆批，拆批按「独立可审查单元」拆，保证前后端一致性能在同一批里核对。

## 测试

红绿循环三条（2026-07-25 tdd skill归档后内联，原文在`~/.claude/_archive-skills/20260725-doctor/tdd/`）：

- **先定seam再写测试**：seam是能观察行为的公共边界。动手前把要测的seam列出来跟用户确认，测试只挂在seam上，不测私有方法不mock内部协作者
- **红在绿前**：先写失败的测试，再写刚好让它过的代码。不提前写将来才需要的
- **一次一片**：一个seam、一个测试、一次最小实现。禁止把测试全写完再实现，批量写的测试验证的是想象中的行为

重构不在循环里，归审查阶段。

- code-writer不写测试。派它时主会话先写失败测试，工作包里给测试文件路径，它的完成标准是让测试变绿，禁止改测试文件
- 写测试的场景：核心业务计算、API、路由、状态管理、复杂验证器解析器、有复现路径的bug修复、用户明确要求
- 不写的场景：UI样式交互状态、文案、配置文件、重命名格式整理、一次性脚本、50行以内输入输出明确的小工具函数
